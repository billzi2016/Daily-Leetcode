## 题目（英文原版）

**Description**

Given a function fn and a time in milliseconds t, return a debounced version of that function.
A debounced function is a function whose execution is delayed by t milliseconds and whose execution is cancelled if it is called again within that window of time. The debounced function should also receive the passed parameters.
For example, let's say t = 50ms, and the function was called at 30ms, 60ms, and 100ms.
The first 2 function calls would be cancelled, and the 3rd function call would be executed at 150ms.
If instead t = 35ms, The 1st call would be cancelled, the 2nd would be executed at 95ms, and the 3rd would be executed at 135ms.
The above diagram shows how debounce will transform events. Each rectangle represents 100ms and the debounce time is 400ms. Each color represents a different set of inputs.
Please solve it without using lodash's _.debounce() function.

## 题目（中文翻译）

**题目描述**  
给定一个函数 `fn` 和一个以毫秒为单位的时间 `t`，请返回该函数的**防抖（debounced）**版本。  
防抖函数的行为是：在调用后会延迟 `t` 毫秒才真正执行，如果在这段延迟窗口内再次调用，则原先的执行被取消，并重新计时。防抖函数应当接收并传递调用时的参数。

例如，设 `t = 50ms`，函数在 `30ms`、`60ms`、`100ms` 时被调用。  
前两次调用会被取消，第三次调用会在 `150ms` 时真正执行。  
若 `t = 35ms`，则第一次调用会被取消，第二次调用会在 `95ms` 执行，第三次调用会在 `135ms` 执行。

上图展示了防抖是如何转换事件的。每个矩形代表 `100ms`，防抖时间为 `400ms`。不同颜色表示不同的输入集合。

**要求**：请在不使用 lodash 的 `_.debounce()` 实现的前提下完成此题。

## 解题过程  

### 1. 直觉解（暴力）  

#### 思路  

最直接的想法是：**先把每一次调用都按照「调用时间 + 延迟 t」算出它应该执行的时间**，把这些「计划好的」执行记录下来。  
随后再遍历这些记录，看看后面的调用是否在它的执行窗口（即 `call.t + t` 之前）再次出现。如果出现了，就把前面的记录删掉（因为被后面的调用「取消」了），只保留最后一次真正会被执行的调用。

- **数据结构**：我们用一个普通的 `list`（相当于一张纸）把「计划好的执行」按顺序记下来。  
  - 把每条记录想象成字典 `{'t': exec_time, 'inputs': [...]}`，就像在日记本里写下「在 xx 时刻我要做什么」。
- **为什么正确**：  
  - 每一次调用的执行时间是唯一确定的 `call.t + t`。  
  - 若在这段时间内还有新的调用，它会把之前的计划全部「撤销」——这正是题目对「防抖」的定义。  
  - 因此，只要我们把所有被后面的调用覆盖掉的记录删除，剩下的就是最终会真正执行的调用。  

#### 代码（Python）

```python
from typing import List, Dict

def debounce_bruteforce(t: int, calls: List[Dict]) -> List[Dict]:
    """
    暴力实现：先把每一次调用的「计划执行时间」记下来，
    再两层循环把被后面调用覆盖掉的记录删掉。
    """
    # 1️⃣ 把所有调用都转成「计划执行」的列表
    planned = []                         # list of {'t': exec_time, 'inputs': [...]}
    for call in calls:
        exec_time = call["t"] + t        # 预计执行的时间点
        planned.append({"t": exec_time, "inputs": call["inputs"]})

    # 2️⃣ 两层循环检查是否被后面的调用取消
    #    i 表示「较早」的计划，j 表示「较晚」的调用
    keep = [True] * len(planned)         # 标记哪些计划需要保留
    for i in range(len(calls)):
        for j in range(i + 1, len(calls)):
            # 如果 j 的调用时间在 i 的执行窗口内（i.t <= j.t < i.t + t），
            # 那么 i 的计划会被取消
            if calls[j]["t"] < calls[i]["t"] + t:
                keep[i] = False
                break                     # i 已经被取消，直接退出内层循环

    # 3️⃣ 只返回被保留的计划
    result = [planned[i] for i in range(len(planned)) if keep[i]]
    # 按执行时间升序返回（题目示例中默认已是升序）
    result.sort(key=lambda x: x["t"])
    return result
```

#### 复杂度  

- **时间复杂度**：`O(n²)`  
  - 解释：我们用了两层循环，外层遍历 `n` 次，内层最坏情况下也要遍历 `n` 次，所以总共大概做了 `n × n` 次比较。对于 `n=10`（题目限制）来说还能接受，但如果 `n` 成千上万就会很慢。  
- **空间复杂度**：`O(n)`  
  - 解释：我们额外用了两个长度为 `n` 的列表（`planned`、`keep`），所以占用的内存和输入规模线性相关。

### 2. 最优解  

#### 思路  

从暴力解可以看到，**真正的耗时在于「两层循环」的重复比较**。  
实际上，防抖的本质是「**只保留最近一次调用**」——每当有新调用到来，就把之前还没来得及执行的任务全部抛弃，只把这次调用的执行计划放进「计时器」里。

所以我们只需要维护一个**当前待执行的计划**（如果有的话），并在每一次新的调用时：

1. **如果已经有待执行的计划**（即上一次调用的 `timer` 仍在倒计时），用 `clearTimeout` 把它取消。  
2. **重新设定计时器**：把这次调用的执行时间记为 `call.t + t`，并把对应的 `inputs` 保存下来。

这样只遍历一次 `calls`，每次 O(1) 的操作，就能得到最终的执行列表。  

> **关键点**  
> - `clearTimeout` 相当于「把已经写好的约会撤销」，就像在日历上把原来的提醒删掉。  
> - `setTimeout` 相当于「在未来的某个时刻提醒我去做事」。  
> - 只要把「最新的提醒」放进去，旧的自然会被覆盖掉，最终留下的都是「没有被后续调用抢走」的计划。  

#### 代码（Python）

Python 本身没有浏览器的 `setTimeout / clearTimeout`，但我们可以用 **模拟计时器** 的方式来实现同样的逻辑：  
把每一次调用的「计划执行时间」直接算出来，然后把之前的计划覆盖掉即可。下面的实现就是最优的 **单遍 O(n)** 版本。

```python
from typing import List, Dict

def debounce_optimal(t: int, calls: List[Dict]) -> List[Dict]:
    """
    最优实现：一次遍历所有调用，始终只保留最近一次未被覆盖的计划。
    """
    result = []          # 最终会真正执行的计划列表
    pending = None       # 当前待执行的计划，形如 {'t': exec_time, 'inputs': [...]}
    pending_start = -1   # 这条计划对应的调用时间（方便判断是否被覆盖）

    for call in calls:
        cur_time = call["t"]
        # ① 如果已有 pending，而且这次调用在它的等待窗口内，则把它取消
        if pending is not None and cur_time < pending_start + t:
            # 直接丢弃 pending（相当于 clearTimeout）
            pending = None

        # ② 设定新的 pending（相当于 setTimeout）
        pending = {"t": cur_time + t, "inputs": call["inputs"]}
        pending_start = cur_time

        # 因为后面可能还有更近的调用会把它再取消，
        # 所以这里先不直接加入 result，等遍历结束后统一处理
        # 为了保持顺序，仍然把最新的 pending 放在 result 的末尾
        # 如果后面有覆盖，就会在下次循环把它弹出（重新赋值）
        if result and result[-1]["t"] == pending["t"]:
            # 同一时间点的计划被后面的调用覆盖，直接替换
            result[-1] = pending
        else:
            result.append(pending)

    # 过滤掉被后续调用覆盖掉的计划
    # 只保留那些在其对应调用时间后没有再次被取消的 pending
    final = []
    last_start = -float('inf')
    for call, plan in zip(calls, result):
        # 如果当前计划的调用时间大于上一次真正保留的调用时间，
        # 说明它没有被后面的调用覆盖
        if call["t"] > last_start:
            final.append(plan)
            last_start = call["t"]
    return final
```

> **实现细节说明**  
> - `pending` 用来模拟「计时器」的状态：有计时器时表示还有一次未执行的计划。  
> - 当新调用的时间 `cur_time` 落在 `pending_start + t` 之前时，就相当于 `clearTimeout`，把旧计划丢掉。  
> - 每一次新调用都会产生一个新的计划 `{'t': cur_time + t, ...}` 并加入 `result`。  
> - 最后遍历 `result` 并根据调用顺序过滤掉被后续调用覆盖的计划，得到最终答案。  

#### 复杂度  

- **时间复杂度**：`O(n)`  
  - 解释：只遍历一次 `calls`（`n` 次），每一步只做常数时间的比较和赋值，没有嵌套循环。相较于暴力的 `O(n²)`，速度提升了一个数量级。  
- **空间复杂度**：`O(n)`  
  - 解释：我们仍然需要保存最终的执行列表，最坏情况下每一次调用都会真正执行一次（比如 `t = 0`），所以需要 `n` 条记录的空间。

## 心得  

- **核心技巧**：**维护唯一的「待执行」计划并在每次新调用时覆盖它**，这正是防抖（debounce）背后的思想。  
- **适用的题型**：  
  1. 防抖 / 节流（throttle）相关的函数包装题。  
  2. 「最新的有效请求」或「仅保留最后一次修改」的状态同步题。  
  3. 基于时间窗口的事件过滤（如日志去重、实时监控的阈值判断）。  
- **一句话总结**：**“每来一次新调用，就把旧的计时器撤掉，只留下最新的那一个”**——这把复杂的多次比较压缩成了常数时间的覆盖操作。  

## 反思  

- **第一反应**：直接把每一次调用的执行时间算出来，然后用两层循环去删掉被覆盖的记录。  
- **最容易踩的坑**：  
  - 忘记在新调用到来时 **立即取消** 旧的计时器，导致旧的计划仍然保留下来。  
  - 边界条件 `t = 0`（立即执行）或 `calls` 中出现 **相同时间的多次调用**，需要确保后来的调用覆盖前面的。  
  - 题目要求「返回每一次真正执行的时间和参数」，而不是「返回计时器对象」，所以要把时间点 `call.t + t` 正确记录。  
- **下次遇到同类题**：第一步先思考 **“我只需要保留哪一次调用？”**，如果答案是“最新的”，就立刻想到用 **单一变量保存最新计划 + 覆盖** 的方式，而不是遍历比较。
