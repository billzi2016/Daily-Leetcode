## 解题过程

### 1. 直觉解（暴力）

#### 思路  

这是一类**取石子游戏**（Stone Removal Game）。  
游戏规则很简单：

1. 桌子上有 `n` 颗石子。  
2. 两位玩家轮流操作，**先手**是 Alice。  
3. 每一次只能一次性取走 **2、3 或 5 颗**石子（这三个数是固定的，像是游戏手册里列出来的合法动作）。  
4. 当轮到某人时，若桌面上没有合法的取法（也就是剩余石子数 < 2），则此人**输**，对手获胜。

> **类比**：把合法取法想成字典里的“单词”。  
> - “单词” = 取走的石子数（2、3、5）  
> - “解释” = 把对应数量的石子从堆里拿走  
> - 查字典的过程就是“看我现在能不能合法取石子”。

我们可以直接**递归**地模拟所有可能的取法：

- 如果当前剩余 `n` 颗石子，遍历三种合法取法 `k ∈ {2,3,5}`。  
- 只要有一种 `k` 使得 **对手在 `n‑k` 颗石子时必败**，那么当前玩家必胜。  
- 如果所有合法 `k` 都导致对手必胜，则当前玩家必败。

递归的**终止条件**是：`n < 2`（没有合法取法），此时**当前玩家输**，返回 `False`。

由于递归会重复计算相同的子问题（比如 `n=7` 可能会从 `n=12`、`n=9` 等多条路径算到），我们用 **记忆化**（把已经算好的 `n` 的结果存进字典）来避免重复工作，这就是 **暴力+备忘录**（Brute‑Force with Memo） 的思路。

#### 代码（Python）

```python
def stoneGameBrute(n: int) -> bool:
    """暴力递归 + 记忆化，判断 Alice 是否能赢"""
    # 记忆化表，key 是当前石子数，value 是是否为先手必胜局面
    memo = {}

    def can_win(remaining: int) -> bool:
        # 1. 备忘录查询
        if remaining in memo:
            return memo[remaining]

        # 2. 递归终止：没有合法的取法，当前玩家输
        if remaining < 2:          # 剩 0 或 1 颗石子，不能取
            memo[remaining] = False
            return False

        # 3. 枚举所有合法取法
        for take in (2, 3, 5):
            if remaining >= take:
                # 对手在剩下的 remaining‑take 颗石子时如果必败，
                # 那么当前玩家就能赢
                if not can_win(remaining - take):
                    memo[remaining] = True
                    return True

        # 4. 所有合法取法都让对手进入必胜局面，当前玩家必败
        memo[remaining] = False
        return False

    return can_win(n)
```

> **关键行中文注释**  
> - `if remaining < 2:` —— 没有合法取法，直接返回 `False`（输）。  
> - `for take in (2, 3, 5):` —— 只遍历题目允许的三种取法。  
> - `if not can_win(remaining - take):` —— 只要有一次取法让对手**必败**，当前局面就是**必胜**。

#### 复杂度

- **时间复杂度**：`O(n)`  
  - 虽然递归看起来像指数级，但记忆化保证每个 `remaining`（0 … n）只被计算一次，每次最多遍历 3 种取法，所以总工作量是 `3 * n`，即 **线性**。  
  - 大白话：就像把 1…n 的每个数字都检查一次，和把 50 本书都读一遍差不多。

- **空间复杂度**：`O(n)`  
  - 记忆化表保存了 `n+1` 个布尔值，递归栈最深也不会超过 `n`（最坏情况每次只取 2 颗），所以使用的额外空间是线性的。

### 2. 最优解

#### 思路  

暴力解已经是 **记忆化递归**，时间已经是 `O(n)`，已经很快。  
但我们可以把递归改写成 **自底向上的动态规划**（DP），消除函数调用的开销，代码更简洁，且更容易推理。

**核心想法**：  
- 用一个数组 `dp[i]` 表示“**当剩余 `i` 颗石子时，先手是否必胜**”。  
- `dp[0] = dp[1] = False`（因为不能合法取石子）。  
- 对于 `i >= 2`，只要存在一种合法取法 `k` 使得 `dp[i - k]` 为 `False`，就说明 `dp[i] = True`（先手可以把对手逼进必败局面）。  
- 否则 `dp[i] = False`。

这一步其实就是把递归的**状态转移**写成了循环。

**类比**：把 `dp` 看成一排灯泡，灯泡亮 (`True`) 表示“先手能赢”。  
我们从左到右依次检查每盏灯：只要左边（`i - k`）有一盏是暗的（`False`），那么当前灯就点亮（`True`），因为先手可以把游戏导向那盏暗灯对应的局面。

#### 代码（Python）

```python
def stoneGameDP(n: int) -> bool:
    """自底向上 DP，返回 Alice 是否能赢"""
    # dp[i] = True 表示剩 i 颗石子时，先手必胜
    dp = [False] * (n + 1)          # 初始化全部为 False

    # 0、1 颗石子时先手必败，已在默认值里
    for i in range(2, n + 1):
        # 检查三种合法取法，只要有一种能让对手进入必败局面即为必胜
        for take in (2, 3, 5):
            if i >= take and not dp[i - take]:
                dp[i] = True
                break               # 已找到必胜取法，结束内部循环

    return dp[n]
```

> **关键行中文注释**  
> - `dp = [False] * (n + 1)` —— 为每个石子数准备一个布尔位，默认都是“先手输”。  
> - `if i >= take and not dp[i - take]:` —— 如果当前可以取 `take` 颗且取后对手必输，则当前局面必胜。  
> - `break` —— 找到一种必胜取法后就不必继续检查其它取法。

#### 复杂度

- **时间复杂度**：`O(n)`  
  - 外层循环遍历 `2 … n`（共 `n‑1` 次），内层最多检查 3 种取法，整体仍是线性。  
  - 与记忆化递归的 `O(n)` 相同，只是省去了函数调用的额外常数开销。

- **空间复杂度**：`O(n)`  
  - 只用一个长度为 `n+1` 的数组 `dp`，没有递归栈。

> 与暴力解对比：两者时间复杂度相同，但 DP 省去了递归的函数调用，实际运行更快、更易于理解。

## 心得

- **核心技巧**：**状态转移**（先手能否必胜） + **动态规划**（自底向上填表）。  
- **适用的题型**（类似思路）：
  1. “取石子游戏”系列（取 1、3、4；取 1、2、5 等）。  
  2. “取硬币游戏”或“取数字游戏”，只要每一步的合法操作是固定的有限集合。  
  3. “博弈论 DP”——如 Nim、取子集游戏等。

- **一句话总结**：**把“我能否让对手陷入必输局面”写成布尔数组，逐步向前推进，即可快速判断先手是否必胜。**

## 反思

- **第一反应**：看到“取石子”立刻想到递归/记忆化——枚举所有合法取法，看是否能让对手输。  
- **最容易踩的坑**：
  - **边界条件**：`n < 2` 时没有合法取法，一定要返回 `False`。  
  - **忘记检查合法取法的上限**：在循环里要先判断 `i >= take`，否则会出现负索引错误。  
  - **记忆化/DP 表的大小**：如果忘记给 `dp` 开 `n+1` 长度，访问 `dp[n]` 会越界。

- **下次遇到同类题**：**第一步先写出状态转移方程**（`dp[i] = any(!dp[i‑k])`），再决定是递归+记忆化还是自底向上 DP。这样思路清晰，代码自然就对了。
