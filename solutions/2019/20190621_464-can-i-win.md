# #464. **我能赢吗** / Can I Win

> 难度：中等 · 标签：Math、Dynamic Programming、Bit Manipulation、Memoization、Game Theory、Bitmask · [LeetCode 链接](https://leetcode.com/problems/can-i-win/)

---

## 题目（英文原版）

**Description**

In the "100 game" two players take turns adding, to a running total, any integer from 1 to 10. The player who first causes the running total to reach or exceed 100 wins.
What if we change the game so that players cannot re-use integers?
For example, two players might take turns drawing from a common pool of numbers from 1 to 15 without replacement until they reach a total >= 100.
Given two integers maxChoosableInteger and desiredTotal, return true if the first player to move can force a win, otherwise, return false. Assume both players play optimally.

**Examples**

**Example 1:**

```
Input: maxChoosableInteger = 10, desiredTotal = 11
Output: false
Explanation:
No matter which integer the first player choose, the first player will lose.
The first player can choose an integer from 1 up to 10.
If the first player choose 1, the second player can only choose integers from 2 up to 10.
The second player will win by choosing 10 and get a total = 11, which is >= desiredTotal.
Same with other integers chosen by the first player, the second player will always win.
```

**Example 2:**

```
Input: maxChoosableInteger = 10, desiredTotal = 0
Output: true
```

**Example 3:**

```
Input: maxChoosableInteger = 10, desiredTotal = 1
Output: true
```

**Constraints**

- 1 <= maxChoosableInteger <= 20
- 0 <= desiredTotal <= 300

## 解题过程

### 1. 直觉解（暴力）

#### 思路  

最直接的想法是**穷举所有可能的出招顺序**，模拟游戏的每一步：

1. 轮到某位玩家时，从剩下的数字中任选一个（`1 … maxChoosableInteger` 中未被使用的）。
2. 把它加到当前的总和 `total` 上。
3. 检查 `total` 是否已经 **≥ desiredTotal**。如果是，当前玩家立刻获胜。
4. 否则，轮到对手继续同样的操作。

这其实是一次 **完整的博弈树搜索**（也叫 *Minimax*），每个节点代表一次“我选了哪个数”，子节点代表对手的所有合法选择。只要在某个节点上**存在一种选择**能够让对手**无论怎么走都输**，那么这个节点就是“我必胜”。

> **数据结构类比**  
> - “已经用过的数字”可以用一个 **集合**（`set`）或 **布尔数组** 来保存，类似于我们平时记“已经买过的商品”。  
> - 博弈树本身就像**家谱树**：根节点是游戏开始，向下每层交替是“我”“你”。

**为什么正确**：因为我们把**所有**合法的对局都遍历了一遍，若有一种走法能保证先手必胜，就一定能在搜索过程中被发现；若没有，则先手必输。

#### 代码（Python）

```python
def canIWin_bruteforce(maxChoosableInteger: int, desiredTotal: int) -> bool:
    # 早期判断：如果目标已经 <= 0，先手直接赢
    if desiredTotal <= 0:
        return True
    # 所有数字之和都不够，先手无论怎么选都不可能赢
    if (maxChoosableInteger * (maxChoosableInteger + 1)) // 2 < desiredTotal:
        return False

    # 递归搜索，used[i] == True 表示数字 i+1 已经被取走
    used = [False] * maxChoosableInteger

    def dfs(current_total: int) -> bool:
        """返回当前玩家是否有必胜策略"""
        for i in range(maxChoosableInteger):
            if used[i]:
                continue          # 这个数字已经被用过，跳过
            next_total = current_total + (i + 1)
            # 如果我这一次直接把总和逼到 >= desiredTotal，直接赢
            if next_total >= desiredTotal:
                return True
            # 否则，轮到对手。先标记这次选择，再递归
            used[i] = True
            opponent_can_win = dfs(next_total)
            used[i] = False     # 恢复现场，回溯
            # 如果对手 **不能** 赢，那说明我这一步必胜
            if not opponent_can_win:
                return True
        # 所有合法选择都让对手有必胜策略，我只能输
        return False

    return dfs(0)
```

> **关键行中文注释** 已写在代码里，帮助理解每一步在做什么。

#### 复杂度

- **时间复杂度**：`O( n! )`（严格来说是 `O(2^n * n)`），因为我们会尝试每一种可能的取数顺序。  
  - `n = maxChoosableInteger ≤ 20`，当 `n` 较大时，`n!` 的增长速度极快，实际运行会超时。
- **空间复杂度**：`O(n)`，主要是递归栈深度和 `used` 数组占用的空间。  

> **大白话**：  
> - `O(n!)` 就像把所有可能的排队顺序都列出来，人数越多，排列组合的数量就会爆炸。  
> - `O(n)` 只是把“已经用了哪些号码”这张小表格保存在内存里。

### 2. 最优解

#### 思路  

暴力解的**瓶颈**在于**大量重复子问题**：同样的“已使用数字集合”和“当前总和”会被不同的路径多次计算。例如，先手先选 3 再选 5，和先手先选 5 再选 3，最后的状态（已用 {3,5}，当前总和相同）是完全一样的，却被重复求解。

**关键优化**：把**状态**抽象成一个**唯一的标识**，并把已经算过的结果记下来（**记忆化搜索 / Memoization**）。  
- 对于 `maxChoosableInteger ≤ 20`，我们可以用 **位掩码（bitmask）** 把“哪些数字已被取走”压缩进一个整数。  
  - 第 `i` 位（从 0 开始）为 `1` 表示数字 `i+1` 已经被使用，`0` 表示还能用。  
  - 这相当于每个数字都有一个**开关**，所有开关一起组成一个**二进制数**，唯一标识当前局面。

**递归公式**（记为 `can_win(mask, cur_total)`）：

> 对于当前玩家，遍历所有还能选的数字 `i`（对应位为 0）：
> - 如果 `cur_total + i >= desiredTotal` → 直接赢，返回 `True`；
> - 否则，假设我选了 `i`，局面变成 `next_mask = mask | (1 << (i-1))`，轮到对手。  
>   如果对手在 `next_mask` 的局面**必输**（即递归返回 `False`），说明我这一步必胜，返回 `True`。

如果所有合法 `i` 都让对手必胜，则我只能输，返回 `False`。

**提前剪枝**：

1. **总和不足**：如果 `1+2+…+maxChoosableInteger < desiredTotal`，连把所有数字都加起来也达不到目标，先手必输，直接返回 `False`。
2. **目标 ≤ 0**：先手一开始就已经满足条件，直接返回 `True`。

**记忆化**：使用字典 `memo[mask] = bool` 保存每个掩码对应的胜负结果。由于同一个 `mask` 对应的 `cur_total` 可以唯一由 `mask` 推算出来（所有已选数字之和），我们只需要 `mask` 这一个键。

#### 代码（Python）

```python
def canIWin(maxChoosableInteger: int, desiredTotal: int) -> bool:
    # ---------- 预处理 ----------
    # 目标已经 <= 0，先手直接赢
    if desiredTotal <= 0:
        return True
    # 所有数字之和仍然不足以达到目标，先手必输
    total_sum = (maxChoosableInteger * (maxChoosableInteger + 1)) // 2
    if total_sum < desiredTotal:
        return False

    # ---------- 记忆化搜索 ----------
    from functools import lru_cache

    @lru_cache(maxsize=None)
    def dfs(mask: int, cur_total: int) -> bool:
        """
        mask: 用 20 位的二进制数表示哪些数字已经被选走。
        cur_total: 当前累计的总和（可以由 mask 推算，但这里直接传进来更直观）。
        返回值: 当前玩家在此局面是否必胜。
        """
        # 遍历所有可能的选择
        for i in range(1, maxChoosableInteger + 1):
            bit = 1 << (i - 1)          # 第 i 位对应的掩码
            if mask & bit:              # 这位已经是 1，说明数字 i 已经被用了
                continue

            next_total = cur_total + i
            # 如果我这一步就把总和逼到 >= desiredTotal，我直接赢
            if next_total >= desiredTotal:
                return True

            # 否则，轮到对手。把 i 标记为已用
            next_mask = mask | bit
            # 如果对手在 next_mask 的局面必输（返回 False），说明我必胜
            if not dfs(next_mask, next_total):
                return True

        # 所有合法选择都让对手必胜，我只能输
        return False

    # 初始局面：没有数字被使用，累计总和为 0
    return dfs(0, 0)
```

> **代码要点**  
> - `1 << (i-1)` 把数字 `i` 对应到二进制的第 `i-1` 位。  
> - `mask & bit` 检查该位是否已经是 1（即数字已被取走）。  
> - `lru_cache` 自动把已经计算过的 `(mask, cur_total)` 结果记下来，等价于手写 `memo` 字典。  

#### 复杂度

- **时间复杂度**：`O( 2^n * n )`（`n = maxChoosableInteger ≤ 20`）。  
  - 每个不同的 `mask` 只会被计算一次，`mask` 的数量最多是 `2^n`（所有子集），每次遍历最多 `n` 个数字。  
  - 与暴力解的 `O(n!)` 相比，指数级的 `2^n` 规模要小得多，能够在几毫秒内跑完（`2^20 ≈ 1,048,576`）。
- **空间复杂度**：`O( 2^n )`。  
  - 递归栈深度最多 `n`，而缓存表 `memo`（或 `lru_cache`）需要存储每个 `mask` 的结果，最多 `2^n` 条记录。

> **对比**：  
> - 暴力解：`O(n!)` → 随着 `n` 增长，几乎不可能在 1 秒内完成。  
> - 最优解：`O(2^n * n)` → 在本题的约束（`n ≤ 20`）下完全可行。

## 心得

- **核心技巧**：**状态压缩 + 记忆化搜索**（即“位掩码 + DP”），把游戏的每个局面抽象成唯一的整数并缓存结果，避免重复计算。
- **适用的题型**  
  1. “取石子”“划分游戏”等需要记录**已使用元素集合**的博弈类题目（如 LeetCode 464、847）。  
  2. “组合数求和”“排列限制”等需要遍历**子集**并判断可行性的 DP/回溯问题。  
- **一句话总结解题钥匙**：  
  > 用二进制位把“哪些数字已经被拿走”压成一个整数，配合记忆化搜索，让每个局面只算一次。

## 反思

- **第一反应**：直接写递归遍历所有可能的出招顺序，感觉最自然，但马上意识到会超时。  
- **最容易踩的坑**  
  1. **提前判断**：忘记判断“所有数字之和不足以达到目标”，会导致不必要的深度搜索。  
  2. **位运算错误**：`1 << (i-1)` 与 `mask & bit` 必须对应，否则会把错误的数字当成已用。  
  3. **递归终止条件**：必须在“当前玩家直接赢”时立刻返回 `True`，否则会继续递归产生错误结果。  
- **下次遇到同类题**：第一步先思考**“如何唯一表示局面？”**（集合、位掩码、字符串等），随后检查是否可以**记忆化**或**DP**，再判断是否需要**提前剪枝**（总和不足、目标已达等）。
