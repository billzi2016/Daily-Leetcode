## 题目（英文原版）

**Description**

You start with an initial power of power, an initial score of 0, and a bag of tokens given as an integer array tokens, where each tokens[i] denotes the value of tokeni.
Your goal is to maximize the total score by strategically playing these tokens. In one move, you can play an unplayed token in one of the two ways (but not both for the same token):
Return the maximum possible score you can achieve after playing any number of tokens.

**Examples**

**Example 1:**

```
Input: tokens = [100], power = 50
Output: 0
Explanation : Since your score is 0 initially, you cannot play the token face-down. You also cannot play it face-up since your power ( 50 ) is less than tokens[0] ( 100 ).
```

**Example 2:**

```
Input: tokens = [200,100], power = 150
Output: 1
Explanation: Play token 1 ( 100 ) face-up, reducing your power to 50 and increasing your score to 1 .
There is no need to play token 0 , since you cannot play it face-up to add to your score. The maximum score achievable is 1 .
```

**Example 3:**

```
Input: tokens = [100,200,300,400], power = 200
Output: 2
Explanation: Play the tokens in this order to get a score of 2 :
The maximum score achievable is 2 .
```

**Constraints**

- 0 <= tokens.length <= 1000
- 0 <= tokens[i], power < 104

## 题目（中文翻译）

你开始时拥有一个初始能量（power），初始得分为 0，另外还有一个由整数数组 `tokens` 构成的令牌袋，其中 `tokens[i]` 表示第 i 个令牌（token）的数值。  
你的目标是通过策略性地使用这些令牌，使得最终得分最大化。

在一次操作中，你可以选择一个尚未使用的令牌，并以以下两种方式之一使用它（同一个令牌不能同时使用两种方式）：

- 如果你当前的能量（power）至少为 `tokens[i]`，可以将第 i 个令牌正面朝上（face up）使用，失去 `tokens[i]` 的能量并获得 1 分（score）。
- 如果你当前的得分（score）至少为 1，可以将第 i 个令牌正面朝下（face down）使用，获得 `tokens[i]` 的能量并失去 1 分（score）。

返回在使用任意数量的令牌后，你能够获得的最大得分（score）。

## 解题过程  

### 1. 直觉解（暴力）  

#### 思路  

最直接的想法是把每一枚未使用的 token 当成两种可能的“操作”：  

1. **正面朝上**（face‑up）：如果当前 `power` 大于等于该 token 的数值，就可以把它翻面，`power` 减去 token 的值，`score` 加 1。  
2. **正面朝下**（face‑down）：如果当前 `score` 大于等于 1，就可以把它翻面，`power` 加上 token 的值，`score` 减 1。  

我们可以把整个游戏过程看成一次 **深度优先搜索**（DFS）或 **回溯**：  
- 每一步挑选一个还没用过的 token（`n` 个 token 中任选一个），  
- 决定是正面朝上还是朝下（如果条件满足），  
- 递归地继续后面的操作。  

搜索到底会遍历所有可能的“玩 token 的顺序 + 选哪种方式”，于是一定能得到最大得分——因为我们把**所有**合法的玩法都枚举了一遍。

> **类比**：想象你在图书馆找一本书。暴力搜索就像把所有书都搬到桌面上，逐一尝试每一本放进背包或不放，直到找到装得最多的那种组合。虽然能找到答案，但过程非常费力。

#### 代码（Python）  

```python
from typing import List

def bagOfTokensScore_bruteforce(tokens: List[int], power: int) -> int:
    n = len(tokens)
    used = [False] * n          # 标记 token 是否已经被使用
    best = 0                    # 记录全局最高分

    def dfs(cur_power: int, cur_score: int):
        nonlocal best
        # 每进入一个状态，都更新一次最高分
        best = max(best, cur_score)

        # 枚举所有还未使用的 token
        for i in range(n):
            if used[i]:
                continue

            # ① 正面朝上（如果有足够的 power）
            if cur_power >= tokens[i]:
                used[i] = True
                dfs(cur_power - tokens[i], cur_score + 1)
                used[i] = False    # 回溯

            # ② 正面朝下（如果已有至少 1 分）
            if cur_score >= 1:
                used[i] = True
                dfs(cur_power + tokens[i], cur_score - 1)
                used[i] = False    # 回溯

    dfs(power, 0)
    return best
```

> 代码里每一次递归都把当前的 `power`、`score` 以及已使用的 token 状态保存下来，遍历完所有分支后 `best` 就是答案。  

#### 复杂度  

- **时间复杂度**：`O(2^n * n)`（指数级）  
  - 每个 token 有三种状态：不使用、正面朝上、正面朝下。最坏情况下会产生约 `3^n` 条分支，但因为正面朝下需要 `score≥1`，实际分支略少。用大白话说，就是 **随 token 数量指数增长**，当 `n` 超过 15 时就几乎不可能跑完。  
- **空间复杂度**：`O(n)`（递归栈 + used 数组）  
  - 只需要记录每层递归的状态，最多 `n` 层。

### 2. 最优解  

#### 思路  

暴力解的瓶颈在于**枚举顺序**：我们一次只考虑一个 token，尝试所有可能的组合，导致指数级爆炸。  
实际上，这道题只关心 **“分数的最大值”**，而不在乎具体用了哪几枚 token。我们可以利用以下两点观察来压缩搜索空间：

1. **想要得分**，必须把 **最小的 token** 当作正面朝上来消耗 `power`。因为消耗越少的 `power`，越容易继续拿到更多分。  
2. **想要恢复 `power`**（在 `power` 不足以正面朝上时），应当把 **最大的 token** 当作正面朝下来换取 `power`，因为这样一次换来的 `power` 最多。

基于这两点，我们可以把 token 按 **从小到大** 排序，然后用 **双指针**（左指针指向最小未使用的 token，右指针指向最大未使用的 token）来模拟游戏：

- **如果当前 `power` ≥ `tokens[left]`**，就正面朝上使用左边的 token：`power -= tokens[left]`，`score += 1`，左指针右移。  
- **否则**（`power` 不够翻最小的 token），**如果 `score` ≥ 1**，我们可以正面朝下使用右边的 token：`power += tokens[right]`，`score -= 1`，右指针左移。  
- 每一步都记录下出现过的最高 `score`，因为在后面可能会因为 “换 `power` 再得分” 而让 `score` 暂时下降，但最高值已经保留下来。  

> **类比**：把 token 想成一堆硬币，左边是面额最小的硬币，右边是面额最大的硬币。想要买东西（得分）时，先用最小的硬币付钱，省钱；钱不够时，就把最大的硬币卖掉换成现金（恢复 `power`），即使这会让你手里的硬币数量少一点。  

这个贪心策略可以在 **一次遍历** 完成，时间主要花在排序上。

#### 代码（Python）  

```python
from typing import List

def bagOfTokensScore(tokens: List[int], power: int) -> int:
    # 1. 先把 token 按从小到大排序
    tokens.sort()                     # O(n log n)

    left, right = 0, len(tokens) - 1  # 双指针：左指向最小，右指向最大
    score = 0                         # 当前得分
    max_score = 0                     # 记录遍历过程中出现的最高得分

    while left <= right:
        # 2. 能正面朝上就上，尽可能拿分
        if power >= tokens[left]:
            power -= tokens[left]     # 消耗 power
            score += 1                # 分数加一
            left += 1                 # 左指针右移，表示这枚 token 已用
            max_score = max(max_score, score)   # 更新最高分
        # 3. power 不足且还有分可以“卖”，则正面朝下换取 power
        elif score > 0:
            power += tokens[right]    # 增加 power
            score -= 1                # 分数减一
            right -= 1                # 右指针左移，表示这枚 token 已用
        # 4. 两种操作都做不了，直接结束
        else:
            break

    return max_score
```

> 关键行的中文注释帮助初学者快速抓住每一步的意义。  

#### 复杂度  

- **时间复杂度**：`O(n log n)`  
  - 主要来自对 `tokens` 的排序（`n` 为 token 数量），排序后只进行一次线性扫描 `O(n)`。用大白话说，就是 **先把东西排好队，然后顺序走一遍**，远比指数级的暴力快得多。  
- **空间复杂度**：`O(1)`（不计排序的原地改动）  
  - 只用了几个整数变量和两个指针，和输入规模无关。

## 心得  

- **核心技巧**：**先把最小的 token 用来得分，必要时用最大的 token 换取 power** 的贪心 + 双指针。  
- **适用的题型**（类似思路）：  
  1. **“分数最大化”** 类的题目，如 *Maximum Points You Can Obtain from Cards*。  
  2. **“资源调配”** 类的题目，如 *Assign Cookies*（用最小的饼干满足最大孩子）。  
  3. **“双端操作”** 类的题目，如 *Deque* 相关的滑动窗口最值。  
- **一句话总结解题钥匙**：**把“花最少的代价换取分数”和“用最贵的代价换回代价”分别对应最左/最右，两端交替贪心即可**。

## 反思  

- **第一反应**：看到“正面朝上/正面朝下”两种互逆的操作，立刻想到**回溯**或**动态规划**，想把所有可能的顺序枚举出来。  
- **最容易踩的坑**：  
  - 忘记在 **正面朝下** 时必须先保证 `score ≥ 1`（否则会出现负分）。  
  - 只记录最终的 `score` 而忽略了中间的最高分——因为在换 `power` 的过程中 `score` 可能会暂时下降。  
  - 对空数组或 `power` 极大/极小的情况没有专门处理，导致无限循环。  
- **下次遇到同类题**，第一步应该思考：**有没有一种“最小/最大”贪心策略可以把资源从两端调度**，而不是直接暴力搜索。这样往往能把时间复杂度从指数级降到线性或 `n log n`。
