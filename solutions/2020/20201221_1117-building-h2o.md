# #1117. 构造 H2O / Building H2O

> 难度：中等 · 标签：Concurrency · [LeetCode 链接](https://leetcode.com/problems/building-h2o/)

---

## 题目（英文原版）

**Description**

There are two kinds of threads: oxygen and hydrogen. Your goal is to group these threads to form water molecules.
There is a barrier where each thread has to wait until a complete molecule can be formed. Hydrogen and oxygen threads will be given releaseHydrogen and releaseOxygen methods respectively, which will allow them to pass the barrier. These threads should pass the barrier in groups of three, and they must immediately bond with each other to form a water molecule. You must guarantee that all the threads from one molecule bond before any other threads from the next molecule do.
In other words:
We do not have to worry about matching the threads up explicitly; the threads do not necessarily know which other threads they are paired up with. The key is that threads pass the barriers in complete sets; thus, if we examine the sequence of threads that bind and divide them into groups of three, each group should contain one oxygen and two hydrogen threads.
Write synchronization code for oxygen and hydrogen molecules that enforces these constraints.

**Examples**

**Example 1:**

```
Input: water = "HOH"
Output: "HHO"
Explanation: "HOH" and "OHH" are also valid answers.
```

**Example 2:**

```
Input: water = "OOHHHH"
Output: "HHOHHO"
Explanation: "HOHHHO", "OHHHHO", "HHOHOH", "HOHHOH", "OHHHOH", "HHOOHH", "HOHOHH" and "OHHOHH" are also valid answers.
```

**Constraints**

- 3 * n == water.length
- 1 <= n <= 20
- water[i] is either 'H' or 'O'.
- There will be exactly 2 * n 'H' in water.
- There will be exactly n 'O' in water.

## 解题过程

### 1. 直觉解（暴力）

#### 思路  

这道题的本质是 **线程同步**：  
- 有两类线程，分别代表氢 (`H`) 和氧 (`O`) 原子。  
- 每当恰好出现 **2 个氢 + 1 个氧** 时，这三条线程才能一起“结合”成一条水分子，然后继续往下执行。  

最直接、最笨的想法是 **让每条线程自己去计数**，把所有正在等待的氢、氧都放进一个公共的列表里，当列表里出现 2 个 H 和 1 个 O 时，就把这三条线程依次释放。  

可以把这个公共列表想象成 **“排队等候的餐桌”**：  
- 每位顾客（线程）来到餐桌后先坐下（放进列表），  
- 餐厅经理会不停检查桌子上是否已经坐满 2 位氢客和 1 位氧客，满足条件就让他们一起吃饭（调用 `releaseHydrogen` / `releaseOxygen`），随后把座位清空，继续接待后面的顾客。

实现细节：

1. 用 **全局计数器** `h_cnt`、`o_cnt` 记录已经到达但还未配对的氢、氧数量。  
2. 用 **互斥锁**（`threading.Lock`）保护计数器的读写，防止两个线程同时修改导致错误。  
3. 用 **条件变量**（`threading.Condition`）让线程在不满足配对条件时**挂起**（`wait`），一旦有新线程到达就 **`notify_all`** 让所有等待的线程重新检查。  

为什么能工作？

- 只要有线程拿到锁，就能安全地检查和更新计数器。  
- 当配对成功（`h_cnt >= 2` 且 `o_cnt >= 1`）时，当前线程负责 **“挑选”** 其中的 2 个氢和 1 个氧，分别调用对应的 `release` 方法，然后把计数器减掉，保证这三条线程已经“结合”。  
- 其它仍在等待的线程会在下一轮配对时再次被挑选。

#### 代码（Python）

```python
import threading
from typing import Callable

class H2O:
    def __init__(self):
        # 互斥锁 + 条件变量（内部已经自带锁）
        self.cond = threading.Condition()
        # 已经到达但未配对的氢、氧数量
        self.h_cnt = 0
        self.o_cnt = 0

    def hydrogen(self, releaseHydrogen: Callable[[], None]) -> None:
        """氢线程入口"""
        with self.cond:                     # 先拿到锁
            self.h_cnt += 1                 # 记录自己来了
            # 只要配对不完整，就一直等
            while self.h_cnt < 2 or self.o_cnt < 1:
                self.cond.wait()           # 挂起，释放锁，等别人唤醒

            # 配对成功：当前氢负责“消耗”一对氢和一氧
            releaseHydrogen()              # 输出 H（或执行实际业务）
            self.h_cnt -= 1                # 已经使用掉一个 H
            # 如果这是第二个氢，说明整套 2H+1O 已经完成
            if self.h_cnt == 0:            # 两个氢都已经调用完
                self.o_cnt -= 1            # 同时把氧也消耗掉
                self.cond.notify_all()     # 唤醒其他等待的线程，准备配对下一分子

    def oxygen(self, releaseOxygen: Callable[[], None]) -> None:
        """氧线程入口"""
        with self.cond:
            self.o_cnt += 1                 # 记录自己来了
            # 必须等到有两个氢才能配对
            while self.h_cnt < 2:
                self.cond.wait()

            releaseOxygen()                # 输出 O
            # 氧本身不立即减计数，等两个氢都完成后再一起减
            # （在 hydrogen 中的 if self.h_cnt == 0 里统一处理）
            # 这里不通知，等氢把整套配对完后再统一 notify_all()
```

> **注意**  
> - `releaseHydrogen` / `releaseOxygen` 只负责**打印**或**执行**对应的原子动作，真正的同步逻辑全部在 `Condition` 里。  
> - 只要 `water` 中的字符顺序满足 `2H + 1O` 的比例，这段代码就能保证输出的顺序被划分为合法的 “HHO” 组合。

#### 复杂度

- **时间复杂度**：`O(k)`（`k` 为线程总数），因为每条线程最多只会进入一次 `wait` / `notify` 循环，循环体里只有常数级的操作。  
- **空间复杂度**：`O(1)`，只用了几个计数器和一个锁，和输入规模无关。

### 2. 最优解

#### 思路  

暴力解已经能正确工作，但它有一个 **性能隐患**：  
- 每当有新线程到达时，所有正在等待的线程都会被 `notify_all`，导致大量 **“虚假唤醒”**（线程被叫醒后发现条件仍不满足，又得重新等待）。  
- 当线程数目很大时，这种不必要的上下文切换会浪费大量 CPU 时间。

**优化目标**：让 **只有真正需要执行的线程** 被唤醒，避免无意义的等待和唤醒。

**关键点**：  
1. **信号量（Semaphore）** 是一种计数型的同步原语，天然适合“资源池”。  
   - 把 **两个氢** 看作 **2 张氢票**，把 **一个氧** 看作 **1 张氧票**。  
   - 当氢线程到来时，尝试 **获取** 一张氢票；当票数为 0 时，氢线程自动阻塞。  
   - 同理，氧线程获取氧票。  
2. 当 **2 张氢票 + 1 张氧票** 都被成功获取后，说明可以组成一条水分子，此时让这三条线程**依次执行** `release`，并在最后把票数 **归还**（即 `release`），为下一条分子准备。  

**实现细节**（一步步推导）：

- **Step 1**：创建三个信号量  
  - `h_sem = Semaphore(2)`  → 最多允许 2 条氢线程同时“进入”。  
  - `o_sem = Semaphore(1)`  → 最多允许 1 条氧线程同时“进入”。  
  - `barrier = Semaphore(0)`（或 `threading.Barrier(3)`）用于让 3 条线程在同一时刻同步，确保 **所有 3 条线程都准备好** 后才真正输出。  

- **Step 2**：氢线程流程  
  ```text
  h_sem.acquire()          # 取一张氢票，票不够会阻塞
  barrier.wait()           # 等待其它两条线程也到达
  releaseHydrogen()
  h_sem.release()          # 把氢票归还，给下一轮使用
  ```
- **Step 3**：氧线程流程（与氢类似，只是票数和信号量不同）  
  ```text
  o_sem.acquire()
  barrier.wait()
  releaseOxygen()
  o_sem.release()
  ```

- **Step 4**：使用 `threading.Barrier(3)` 可以自动把 3 条线程聚在一起，等到第 3 条线程到达时一起放行，保证 **同一分子里的 3 条线程顺序不交叉**。  

**为什么更好？**  
- 只有恰好需要的 2 条氢和 1 条氧会被唤醒，其他线程仍然在各自的信号量里阻塞，根本不参与调度。  
- `Barrier` 负责一次性放行 3 条线程，避免了手动计数和 `notify_all` 带来的“假唤醒”。  
- 整体思路更简洁、可读性更高，也更贴近并发编程的常用模式。

#### 代码（Python）

```python
import threading
from typing import Callable

class H2O:
    def __init__(self):
        # 只能同时让 2 个氢线程进入
        self.h_sem = threading.Semaphore(2)
        # 只能同时让 1 个氧线程进入
        self.o_sem = threading.Semaphore(1)
        # 3 条线程聚在一起后统一放行
        self.barrier = threading.Barrier(3)

    def hydrogen(self, releaseHydrogen: Callable[[], None]) -> None:
        """氢线程入口"""
        self.h_sem.acquire()          # 取氢票，若票数为 0 则阻塞
        self.barrier.wait()           # 等待另外两条线程（1 氢 + 1 氧）到达
        releaseHydrogen()             # 真正执行输出 H
        self.h_sem.release()          # 归还氢票，供下一轮使用

    def oxygen(self, releaseOxygen: Callable[[], None]) -> None:
        """氧线程入口"""
        self.o_sem.acquire()          # 取氧票，若票数为 0 则阻塞
        self.barrier.wait()           # 等待另外两条线程（2 氢）到达
        releaseOxygen()               # 输出 O
        self.o_sem.release()          # 归还氧票，供下一轮使用
```

> **运行说明**  
> - `releaseHydrogen` 与 `releaseOxygen` 只负责**打印**字符（或执行业务），不需要关心同步。  
> - 由于 `Barrier` 的内部实现会在第 3 条线程调用 `wait()` 时一次性释放所有等待的线程，保证了同一水分子内部的输出顺序是 **任意**（只要是 2 H + 1 O），且 **不会交叉** 到下一分子。

#### 复杂度

- **时间复杂度**：`O(k)`，每条线程只会 **一次** `acquire`、一次 `wait`、一次 `release`，全部是常数时间操作。  
  - 与暴力解相比，没有了 `notify_all` 带来的额外唤醒开销，实际运行更快。  
- **空间复杂度**：`O(1)`，只用了 3 个信号量/屏障对象，和线程数量无关。

## 心得

- **核心技巧**：利用 **信号量**（计数资源）和 **Barrier**（多线程同步点）实现“恰好 2H + 1O” 的配对。  
- **适用场景**：  
  1. **固定比例配对**（例如 “Producer‑Consumer” 中 1:2、3:1 的生产者‑消费者）  
  2. **分批处理**（如每 N 条记录一起写磁盘）  
  3. **多线程分组同步**（如并行计算的阶段性 barrier）  

> **解题钥匙**：把“需要的资源数”抽象成信号量的票数，让线程先抢票，再在同一个 barrier 上集合。

## 反思

- **第一反应**：看到“2 个氢 + 1 个氧”立刻想到计数和等待，先想用共享变量 + `Condition`。  
- **最容易踩的坑**  
  - **计数错误**：忘记在氢线程里统一把氧的计数也减掉，导致氧票永远不归还。  
  - **死锁**：如果在 `hydrogen` 里提前 `release` 票，可能出现后面的氧一直等不到票的情况。  
  - **Barrier 的复用**：`Barrier` 在一次放行后会自动重置，若手动调用 `reset` 或在异常情况下没有全部到齐，会导致后面的线程永久阻塞。  

- **下次遇到同类题**：第一步先思考 **“每类线程需要多少配额”**，把配额映射到 **Semaphore**；随后判断是否需要 **一次性同步**（使用 `Barrier`）或 **逐步计数**（使用 `Condition`）。这样可以快速定位最合适的并发原语，避免繁琐的手动计数与唤醒。
