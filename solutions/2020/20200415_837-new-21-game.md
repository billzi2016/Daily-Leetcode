# #837. 新 21 游戏 / New 21 Game

> 难度：中等 · 标签：Math、Dynamic Programming、Sliding Window、Probability and Statistics · [LeetCode 链接](https://leetcode.com/problems/new-21-game/)

---

## 题目（英文原版）

**Description**

Alice plays the following game, loosely based on the card game "21".
Alice starts with 0 points and draws numbers while she has less than k points. During each draw, she gains an integer number of points randomly from the range [1, maxPts], where maxPts is an integer. Each draw is independent and the outcomes have equal probabilities.
Alice stops drawing numbers when she gets k or more points.
Return the probability that Alice has n or fewer points.
Answers within 10-5 of the actual answer are considered accepted.

**Examples**

**Example 1:**

```
Input: n = 10, k = 1, maxPts = 10
Output: 1.00000
Explanation: Alice gets a single card, then stops.
```

**Example 2:**

```
Input: n = 6, k = 1, maxPts = 10
Output: 0.60000
Explanation: Alice gets a single card, then stops.
In 6 out of 10 possibilities, she is at or below 6 points.
```

**Example 3:**

```
Input: n = 21, k = 17, maxPts = 10
Output: 0.73278
```

**Constraints**

- 0 <= k <= n <= 104
- 1 <= maxPts <= 104

## 题目（中文翻译）

Alice 正在玩一种 loosely 基于纸牌游戏 “21” 的游戏。  
Alice 初始得分为 0 分，并在得分小于 `k` 时不断抽取（draw）数字。每次抽取时，她会随机获得一个整数分数，范围为 `[1, maxPts]`，其中 `maxPts` 为给定的整数。每次抽取相互独立，且各个结果出现的概率相等。  
当 Alice 的得分达到 `k` 分或更高时，她会停止抽取。  

返回 Alice 最终得分不超过 `n` 分的概率。  
只要答案与真实值的误差在 `10^-5` 以内，即被视为正确。

## 示例

**输出**: `1.00000`  
**解释**: Alice 只抽取一次卡牌，然后停止。

### 示例 2
**输入**: `n = 6, k = 1, maxPts = 10`  
**输出**: `0.60000`  
**解释**: Alice 只抽取一次卡牌，然后停止。  
在 10 种可能的抽取结果中，有 6 种使她的得分不超过 6 分。

### 示例 3
**输入**: `n = 21, k = 17, maxPts = 10`  
**输出**: `0.73278`

- `1 <= maxPts <= 10^4`

## 解题过程  

### 1. 直觉解（暴力）

#### 思路  

最直接的想法是 **模拟** 所有可能的抽卡过程，然后统计满足「最终得分 ≤ n」的情况占总情况的比例。

- **数据结构**：我们可以把每一次抽卡的所有可能得分看成一棵「决策树」。树的每个节点记录当前的累计分数 `score`，从根节点（0 分）开始向下展开。  
  - 这棵树的每一层对应一次抽卡。  
  - 每个分支相当于「抽到 1、2、…、maxPts」这 `maxPts` 种等概率结果。  
- **为什么正确**：遍历完整棵树，就等价于把所有「抽卡序列」枚举出来。统计其中最终分数在 `[k, n]`（因为抽卡会在达到 `k` 时立即停止） 的比例，就是题目要求的概率。  

> **类比**：把这棵树想成一本「选择题答案本」——每一页有 `maxPts` 条答案，翻到第 `k` 页就停下来。我们只需要统计最终得分不超过 `n` 的答案页数占总页数的比例。

#### 代码（Python）

```python
import itertools
from collections import deque

def new21Game_bruteforce(n: int, k: int, maxPts: int) -> float:
    """
    暴力枚举所有抽卡序列（仅在数据规模极小的情况下可用）。
    """
    # 当已经达到或超过 k 时，游戏直接结束，不再继续抽卡
    # 用 BFS（广度优先搜索）遍历所有可能的得分
    q = deque([0])          # 队列里存放当前的累计得分
    total_cases = 0         # 所有可能的抽卡序列数量
    success_cases = 0       # 最终得分 ≤ n 的序列数量

    while q:
        score = q.popleft()
        # 已经停下来（score >= k），统计结果
        if score >= k:
            total_cases += 1
            if score <= n:
                success_cases += 1
            continue

        # 还没到 k，继续抽一张卡
        for pts in range(1, maxPts + 1):
            q.append(score + pts)

    # 由于每条路径的概率相同，直接用计数求比例
    return success_cases / total_cases
```

> **注意**：上述实现会产生指数级别的状态数（每一步都分叉 `maxPts` 条），只能在 `k、maxPts` 极小（比如 ≤ 5）时跑得完。

#### 复杂度  

- **时间复杂度**：`O(maxPts^k)`（每一次抽卡都有 `maxPts` 种可能，最多抽 `k` 次），这就是所谓的 **指数级**，随着 `k` 增大会非常慢。  
- **空间复杂度**：`O(maxPts^k)`，因为队列里最多会同时保存同一层的所有状态，也同样是指数级。

### 2. 最优解  

#### 思路  

暴力解慢的根源在于 **大量重复计算**：很多不同的抽卡序列会得到相同的累计得分。例如，`[1,2]` 与 `[2,1]` 都得到 `3` 分，但我们会把它们当成两条不同的路径去遍历。  
我们可以把注意力从「序列」转移到「得分」本身：只要知道「当前累计得分为 `i`」的概率，就可以推导出「下一个得分为 `i+1、i+2、…、i+maxPts`」的概率。

这正是 **动态规划（DP）** 的思想：  

- 设 `dp[x]` 为「在游戏结束前，累计得分恰好为 `x`」的概率。  
- 初始状态：`dp[0] = 1`（游戏一开始一定是 0 分），其余为 0。  
- 转移公式（当 `x < k` 时仍然会继续抽卡）：

\[
dp[x + t] \;+=\; dp[x] \times \frac{1}{maxPts}, \quad \forall t \in [1, maxPts]
\]

也就是说，若当前分数是 `x`，则抽到每一个 `t` 的概率都是 `1/maxPts`，于是 `x+t` 的概率要累加 `dp[x]/maxPts`。

**直接套用公式会是 O(k·maxPts)**，因为对每个 `x < k` 都要遍历 `maxPts` 次。  
这仍然不够快（在最坏情况下 `k = 10^4`、`maxPts = 10^4`，会达到 10⁸ 次运算）。

#### 滑动窗口优化  

观察转移公式：

\[
dp[i] = \frac{1}{maxPts} \times (dp[i-1] + dp[i-2] + \dots + dp[i-maxPts])
\]

这里的 `dp[i]` 只和前 `maxPts` 个状态的和有关。我们可以维护一个 **滑动窗口** `windowSum`，它始终等于最近 `maxPts` 个 `dp` 值的和。每算出一个新的 `dp[i]`，只需要：

1. 把 `dp[i-1]` 加进窗口（因为它现在进入了最近 `maxPts` 范围）  
2. 如果窗口长度超过 `maxPts`，就把最早的 `dp[i-maxPts-1]` 移出窗口  

这样每次计算 `dp[i]` 只用 **O(1)** 的时间，总体复杂度降到 **O(k + maxPts)**，在题目限制下完全可以接受。

**终止条件**：一旦分数达到 `k`，游戏立刻停止，不再抽卡。因此我们只需要计算 `dp[0] … dp[k-1]`，以及 `dp[k] … dp[n]`（这些是「已经停止」的状态）。最终答案是 `dp[k] + dp[k+1] + … + dp[n]` 的和。

#### 代码（Python）

```python
def new21Game(n: int, k: int, maxPts: int) -> float:
    """
    动态规划 + 滑动窗口，时间 O(k + maxPts)，空间 O(k + maxPts)
    """
    # 特例：如果 k == 0，游戏一开始就停止，必然得分为 0，满足 n >= 0
    if k == 0 or n >= k + maxPts:
        # 当 n 足够大（>= k+maxPts）时，所有可能的结束分数都 ≤ n，概率为 1
        return 1.0

    dp = [0.0] * (n + 1)   # dp[i] 为累计得分恰好为 i 的概率
    dp[0] = 1.0             # 初始分数为 0 的概率是 100%

    window_sum = 1.0        # 当前窗口内 dp 值的和，初始只有 dp[0]
    result = 0.0            # 最终满足 “≤ n” 的概率累计

    # 计算 dp[1] … dp[n]
    for i in range(1, n + 1):
        # 根据滑动窗口公式得到 dp[i]
        dp[i] = window_sum / maxPts

        # 只有当 i < k 时，游戏仍会继续抽卡，dp[i] 需要加入窗口
        if i < k:
            window_sum += dp[i]          # 新的 dp[i] 进入窗口
        else:
            # i >= k，游戏已经停止，这些概率直接计入答案
            result += dp[i]

        # 若窗口长度已超过 maxPts，需要把最旧的 dp 值剔除
        if i - maxPts >= 0:
            window_sum -= dp[i - maxPts]

    return result
```

> **代码要点注释**  
- `if k == 0 or n >= k + maxPts:` 这两个特例可以让函数在极端输入下立即返回 `1.0`，避免不必要的循环。  
- `window_sum` 维护的是「最近 `maxPts` 个仍在抽卡状态的 `dp`」之和。  
- 当 `i >= k` 时，表示已经到达或超过停止阈值，这时 `dp[i]` 不再会被后续抽卡影响，直接累加到 `result`。  
- `i - maxPts >= 0` 时，把最早进入窗口的 `dp` 移出，以保持窗口大小恰好为 `maxPts`。

#### 复杂度  

- **时间复杂度**：`O(n)`（实际上只需要遍历到 `max(k, n)`，但 `n ≤ 10⁴`，完全可接受）。  
  - 与暴力解的 `O(maxPts^k)` 相比，**从指数级降到了线性级**，速度快了几个数量级。  
- **空间复杂度**：`O(n)`，存储 `dp` 数组。若进一步压缩，只保留最近 `maxPts` 项，也可以做到 `O(maxPts)`，但对本题的约束来说没有必要。

## 心得  

- **核心技巧**：把「抽卡序列」的概率累加转换为「状态转移」的动态规划，再利用 **滑动窗口** 把每一步的求和从 `O(maxPts)` 降到 `O(1)`。  
- **适用场景**：  
  1. 「固定长度窗口内求和」的 DP 题，如「剑指 Offer 63. 股票的最大利润」的窗口 DP 变形。  
  2. 「有限步数的随机过程」求期望或概率的题目，如「464. 我能否在 2 秒内得到答案？」的概率 DP。  
  3. 「限制步长的计数」类题，如「322. 零钱兑换」的 DP（只不过这里是概率而已）。  
- **一句话总结**：**把“所有可能的抽卡路径”压缩成“每个得分的出现概率”，用滑动窗口把转移公式变成常数时间**。

## 反思  

- **第一反应**：直接想要枚举所有抽卡组合，写递归或 BFS。这样思路清晰，却忽视了指数爆炸的危险。  
- **最容易踩的坑**：  
  - **边界条件**：`k == 0`（游戏直接结束）和 `n >= k + maxPts`（所有可能的结束分数都 ≤ n）需要提前返回 `1.0`。  
  - **窗口移除时机**：必须在 `i - maxPts >= 0` 时才减去对应的 `dp`，否则窗口会多算旧的概率。  
  - **浮点误差**：累加很多小概率会产生误差，但题目允许 `1e-5` 的误差范围，使用 `float` 完全足够。  
- **下次类似题的第一步**：先把问题抽象为「状态概率/计数」的 DP，检查转移公式是否只依赖「固定数量」的前置状态，如果是，就考虑使用 **滑动窗口** 或 **前缀和** 来加速。
