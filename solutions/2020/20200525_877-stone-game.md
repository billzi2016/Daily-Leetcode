# #877. 石子游戏 / Stone Game

> 难度：中等 · 标签：Array、Math、Dynamic Programming、Game Theory · [LeetCode 链接](https://leetcode.com/problems/stone-game/)

## 题目（英文原版）

**Description**

Alice and Bob play a game with piles of stones. There are an even number of piles arranged in a row, and each pile has a positive integer number of stones piles[i].
The objective of the game is to end with the most stones. The total number of stones across all the piles is odd, so there are no ties.
Alice and Bob take turns, with Alice starting first. Each turn, a player takes the entire pile of stones either from the beginning or from the end of the row. This continues until there are no more piles left, at which point the person with the most stones wins.
Assuming Alice and Bob play optimally, return true if Alice wins the game, or false if Bob wins.

**Examples**

**Example 1:**

```
Input: piles = [5,3,4,5]
Output: true
Explanation: 
Alice starts first, and can only take the first 5 or the last 5.
Say she takes the first 5, so that the row becomes [3, 4, 5].
If Bob takes 3, then the board is [4, 5], and Alice takes 5 to win with 10 points.
If Bob takes the last 5, then the board is [3, 4], and Alice takes 4 to win with 9 points.
This demonstrated that taking the first 5 was a winning move for Alice, so we return true.
```

**Example 2:**

```
Input: piles = [3,7,2,3]
Output: true
```

**Constraints**

- 2 <= piles.length <= 500
- piles.length is even.
- 1 <= piles[i] <= 500
- sum(piles[i]) is odd.

## 题目（中文翻译）

Alice 和 Bob 正在玩一局石子堆（piles）游戏。若干个石子堆按顺序排列成一行（row），堆的数量为偶数，每个堆包含正整数个石子 `piles[i]`。  
游戏目标是最终拥有最多的石子。所有堆中的石子总数为奇数，因而不会出现平局。  

Alice 和 Bob 交替行动，Alice 先手。每回合，玩家只能从当前行的最左端或最右端取走整堆石子。游戏持续进行，直至所有堆被取完，此时石子数较多的玩家获胜。  

在双方都采用最优（optimal）策略的前提下，若 Alice 能赢则返回 `true`，否则返回 `false`。

**示例 1**  
**输入**: `piles = [5,3,4,5]`  
**输出**: `true`  
**解释**:  
Alice 先手，她只能取走最左端的 5 或最右端的 5。  
- 若她取走左端的 5，剩余的行变为 `[3,4,5]`。  
  - 若 Bob 取走 3，行变为 `[4,5]`，Alice 再取走 5，累计得到 10 分获胜。  
  - 若 Bob 取走最右端的 5，行变为 `[3,4]`，Alice 再取走 4，累计得到 9 分获胜。  
这表明取走左端的 5 是 Alice 的必胜手段，因此返回 `true`。

**示例 2**  
**输入**: `piles = [3,7,2,3]`  
**输出**: `true`  

**约束条件**  
- `2 <= piles.length <= 500`  
- `piles.length` 为偶数。  
- `1 <= piles[i] <= 500`  
- `sum(piles[i])` 为奇数。

## 解题过程

### 1. 直觉解（暴力）

#### 思路  

最直接的想法是**模拟所有可能的取石方式**，把每一步的选择（取左端还是右端）都枚举下来，直到所有石子都被取完。  
这就像在玩“取石子游戏”的树形图，每个节点代表当前剩余的石子序列，向左分支代表取左端，向右分支代表取右端。我们把每一次取到的石子数量累计到对应玩家的得分上，最后比较 Alice 与 Bob 的总分，返回 Alice 是否能赢。

> **数据结构类比**  
> - 这里用的递归调用栈类似于“记事本”，记录我们当前在第几层（哪一步）以及剩下的石子序列。  
> - 为了避免重复计算，同样的子序列会出现多次（比如 `[3,4,5]` 既可能是 Alice 第一次取左边后出现，也可能是 Bob 取右边后出现），我们可以用**哈希表**（Python 的 `dict`）把已经算好的子序列结果记下来，就像查字典一样：键是 `(左指针, 右指针)`，值是当前玩家在这段区间能得到的最大分数。

**为什么这个方法正确**  
因为我们枚举了**所有合法的取石顺序**，并且每一种顺序都按照“双方都最优”来计算得分（递归里让对手也取最大），所以最终得到的结果必然是最优解。

#### 代码（Python）

```python
from functools import lru_cache
from typing import List

def stoneGame_bruteforce(piles: List[int]) -> bool:
    """
    暴力递归 + 记忆化搜索（相当于把已经算过的子问题存进哈希表）
    返回 True 表示 Alice 能赢
    """
    n = len(piles)

    @lru_cache(maxsize=None)          # 用 dict 缓存 (left, right) 的结果
    def best(left: int, right: int) -> int:
        """在 piles[left:right+1] 这段区间里，先手玩家能获得的最大分数"""
        if left == right:               # 只剩一堆石子，先手只能拿走它
            return piles[left]

        # 先手若取左端，剩下的区间交给对手，自己得到 left 的石子 +（总和 - 对手能得到的最大分数）
        take_left = piles[left] + (sum(piles[left+1:right+1]) - best(left+1, right))
        # 先手若取右端，同理
        take_right = piles[right] + (sum(piles[left:right]) - best(left, right-1))

        # 先手会选更大的那种
        return max(take_left, take_right)

    total = sum(piles)
    alice = best(0, n-1)                # Alice 先手能得到的最大分数
    return alice > total - alice        # Alice 分 > Bob 分 → 赢
```

#### 复杂度

- **时间复杂度**：`O(2^n)`（没有记忆化时）  
  解释：每一步都有两种选择，深度为 `n`，所以会产生 `2 * 2 * … * 2 = 2^n` 条路径。  
  加上记忆化后，每个 `(left, right)` 只会被计算一次，状态数是 `n*(n+1)/2 ≈ O(n²)`，每次转移需要 `O(1)`（若事先准备前缀和），所以实际时间是 `O(n²)`，但在最朴素实现里仍然会出现 `O(2^n)` 的指数爆炸。

- **空间复杂度**：`O(n²)`  
  解释：缓存表需要存 `n²/2` 条记录，每条记录占用常数空间；递归栈的深度最坏为 `n`，同样是线性空间。

### 2. 最优解

#### 思路  

从暴力解可以看到，**瓶颈**在于我们每一步都要遍历所有可能的取法，导致指数级的搜索。  
要想优化，需要利用**游戏的特殊结构**：

1. **石堆数目是偶数**，而且**总石子数是奇数**（保证不会平局）。  
2. 玩家每回合只能从 **两端** 取石子，这意味着在整局游戏结束后，**Alice 必定拿到偶数编号或奇数编号的石堆的全部**（把原数组的下标分为奇偶两类）。  
   - 设下标从 `0` 开始，偶数位集合为 `E`，奇数位集合为 `O`。  
   - 因为堆数是偶数，`|E| = |O|`。  
   - Alice 第一次可以任选左端或右端，假设她拿走了左端的 **偶数** 堆（下标 0），那么剩下的序列首端就是 **奇数** 堆；此后每轮 Bob 只能从两端取走 **奇数** 堆或 **偶数** 堆中的一个，而 Alice 则可以始终保证自己取走 **同一类（偶数或奇数）** 的所有堆。  

3. 因此，Alice 只需要比较 **两类堆的总石子数**，选取石子总和更大的那一类去“抢”。  
   - 若 `sum(E) > sum(O)`，Alice 在第一回合就取走左端的偶数堆（或右端的偶数堆），随后每次都通过镜像策略（如果 Bob 取走了奇数堆，Alice 再取走对应的偶数堆）确保自己最终拿走所有偶数堆。  
   - 若 `sum(O) > sum(E)`，同理让 Alice 先取奇数堆。  

因为总石子数是奇数，`sum(E)` 与 `sum(O)` 必不相等，必有一方更大，**Alice 总能保证赢**。

> **核心技巧：奇偶分组 + 镜像策略**  
> 这是一种**博弈论**中的**必胜策略**，不需要真正的 DP，只要用数学推导即可。

#### 代码（Python）

```python
from typing import List

def stoneGame(piles: List[int]) -> bool:
    """
    最优解：只要比较奇数位和偶数位石子总和，较大的那一类 Alice 在第一步就锁定，
    之后通过“镜像取石”保证自己拿走全部该类堆，从而必胜。
    由于题目保证总石子数为奇数，必有一方更大，所以直接返回 True。
    """
    # 实际上直接返回 True 就可以，但这里演示完整的奇偶比较过程
    even_sum = sum(piles[i] for i in range(0, len(piles), 2))  # 0、2、4...
    odd_sum  = sum(piles[i] for i in range(1, len(piles), 2))  # 1、3、5...

    # Alice 只要先抢总和更大的那一类即可必胜
    return even_sum > odd_sum or odd_sum > even_sum   # 必然为 True
```

> **说明**：  
> - 第 4 行的 `range(0, len(piles), 2)` 相当于在数组里挑出“偶数位”。  
> - 第 5 行的 `range(1, len(piles), 2)` 挑出“奇数位”。  
> - 最后比较两者大小，题目已保证两者不相等，故一定返回 `True`。

#### 复杂度

- **时间复杂度**：`O(n)` — 只遍历一次数组，线性时间。  
  与暴力解的 `O(2^n)` 或 `O(n²)` 相比，快了几个数量级。

- **空间复杂度**：`O(1)` — 只使用了常数个变量（`even_sum`, `odd_sum`），不随输入规模增长。

## 心得

- **核心技巧**：利用 **奇偶分组** 与 **必胜镜像策略**（Game Theory 中的“先手必胜”思路）直接判断胜负。  
- **适用题型**  
  1. `Stone Game II`（需要 DP，但仍可利用前缀和简化状态转移）  
  2. `Predict the Winner`（同样是两端取数的博弈，可用 DP）  
  3. `Deque` 类的取数游戏（如“取牌游戏”）  
- **一句话总结解题钥匙**：**“先手只要锁定石子总和更大的奇偶集合，就能通过镜像取石把所有该类石子抢走”。**

## 反思

- **第一反应**：看到“从两端取石子，双方最优”，立刻想到**递归/DP**，因为这类游戏常见于“博弈 DP”。  
- **最容易踩的坑**  
  - 忘记利用**堆数是偶数**这一关键信息，导致做了不必要的复杂 DP。  
  - 没注意**总石子数是奇数**，会误以为可能出现平局，需要额外处理平局情况。  
- **下次遇到同类题**：第一步先检查**题目是否给出了奇偶、总和或其他全局约束**，如果有，尝试用**数学/博弈论的必胜策略**快速判断，而不是直接套 DP。这样往往能把时间复杂度从指数级或二次方降到线性甚至 O(1)。
